# DAST CLI — command & flag reference
_Generated by `dast commands` from the argparse parsers; defaults from `config/scanner/default.env`. Do not edit by hand — edit the `help=` / `description` strings in the code and regenerate._

**Value column**
- `a / b` — pick **exactly one**
- `a, b` — a list; choose **any number** (comma-separated)
- `<int>` `<float>` `<url>` `<path>` `<string>` — a free value of that kind
- `—` — a **switch**: takes no value, its presence sets it

## 1 · Commands

| command | arguments | purpose |
|---|---|---|
| `dast <target>` | target | the whole chain: scan → triage → verify → report |
| `dast scan <target>` | target | Scan a target: Noir static extraction seeds ZAP's site tree, then a bounded spider and active scan write the raw alerts and an HTTP-exchange sidecar. |
| `dast triage <run_id>` | run_id | Triage a finished scan: join ZAP alerts to Noir endpoints, then run the deterministic arm and the LLM arm; writes ``triage.json``. |
| `dast verify <run_id>` | run_id | Verify triaged findings with independent tools — one bounded loop per finding, the third and last reading (after the deterministic table and LLM triage): a tool actually trying the attack, recorded confirmed / refuted / inconclusive / not-attempted. |
| `dast report <run_id>` | run_id | Merge the three readings into a SARIF 2.1.0 report and a Markdown summary (``dast report``). |
| `dast static-analysis <target-or-run>` | target-or-run | Standalone SAST + SCA static-analysis findings (Semgrep + OSV-Scanner): run both over the target's source tree and write their SARIF unmodified into a run directory. |
| `dast harness <sheet>` | sheet | The configuration harness: a sheet of runs (config/harness/<name>.yml) executed unattended into one comparison table. |
| `dast cve <run-id> [<run-id>]` | run-id | The correctness axis (dast cve): the project's only external measure of correctness (everything else is internal agreement), which is why each target is pinned to a CVE-bearing version. |
| `dast costs` | — | The record of every run this project has produced — one row per stage-run, oldest first: wall time, cost, peak resource use and tool provenance. |
| `dast commands` | — | regenerate the command & flag reference (COMMANDS.md) from the live argparse parsers. |

## 2 · Shared flags

Flags that reach more than one stage — an option reaches every stage that means one setting by it. The **stages** column says which; where a same-named flag configures each stage separately (`--dry-run`), the env column lists the per-stage variables.

| flag | value | stages | env | default | description |
|---|---|---|---|---|---|
| `--env-file` | `<path>` | all |  |  | Configuration file for this stage. It fills any setting not passed as a flag; an explicit flag always wins over it.<br>Falls back to config/scanner/.env; keys come from a secrets.env beside the file named here. |
| `--data-dir` | `<path>` | all |  | `data/runs` | Where this run's directory is created. |
| `--force` | `—` | all |  | `off` | Run even though another process holds this stage's lock on the run directory. Overrides the refusal; it does not coordinate the two runs. |
| `--out-suffix` | `<string>` | Triage, Verify, Report |  |  | Suffix the output artifact: triage-<ts>-<suffix>.json. Keeps a model-comparison run alongside the baseline instead of replacing it.<br>verify reads it back with --in-suffix; shared with verify/report so a suffixed variant flows through the chain. |
| `--in-suffix` | `<string>` | Verify, Report |  |  | Which triage variant to verify (triage-<SUFFIX>.json); an empty string picks the base triage.json. The case for it is verifying ONE stored triage several times under different settings — the outputs must differ in name while the input must not.<br>Falls back to --out-suffix, which is what a `triage verify` sequence wants (there the same suffix names both). |
| `--auth` | `none / user / admin` | Scan, Verify | SHARED_AUTH_MODE | `none` | Scan authenticated as the target's seeded 'user' or 'admin' account, or 'none' for anonymous. Most of the CVE cluster sits behind login, so this is the biggest lever on detection rate.<br>Runs at each mode are separate and not comparable across modes. |
| `--dry-run` | `—` | Triage, Verify | TRIAGE_DRY_RUN / VERIFY_DRY_RUN | `off` | Write the prompts that would be sent and stop, spending nothing.<br>Set it via the env only deliberately — it turns a real run into a no-op. |
| `--prompt-cache, --no-prompt-cache` | `—` | Triage, Verify | SHARED_PROMPT_CACHE | `on` | Mark a cacheable stable prefix on the multi-turn calls. Caching changes no output — a hit returns the tokens the model would have computed anyway. Synthesis and the verification loop cache heavily (they re-send a large stable prefix); pass 1 barely does.<br>--no-prompt-cache is the off form, for pricing the saving. |
| `--oracle` | `—` | Scan, Triage, Verify | SHARED_ORACLE | `off` | Oracle-guided (ceiling) mode: additionally seed the benign sinks of this target's documented CVE markers (cve-markers.yml `seed:`) — surfaces no static extractor names and no crawler discovers. Measures what the pipeline could detect GIVEN we point the scanner at the known sinks; the gap from a blind run is what discovery costs.<br>Changes the scan's configuration digest, so an oracle run and a blind run never share a corpus. The LLM stages take the same flag to be TOLD the vulnerabilities — this is its scan-stage half. |
| `--retrieval` | `push / pull` | Triage, Verify | TRIAGE_RETRIEVAL / VERIFY_RETRIEVAL | `push` | How pass 1 gets its evidence: `push` (the assembler attaches the exchange and the handler source to every prompt — the A/B baseline) or `pull` (a minimal pack plus a manifest of what is retrievable, and the model asks the read-only context MCP server for what it needs).<br>`pull` is bounded by --retrieval-max-calls. |
| `--retrieval-max-calls` | `<int>` | Triage, Verify | TRIAGE_RETRIEVAL_MAX_CALLS / VERIFY_RETRIEVAL_MAX_CALLS | `6` | Retrievals one pass-1 call may make before the tools are withdrawn and the model must answer. Deliberately small: the question is whether a model asks for the RIGHT evidence, and a generous budget answers a different one.<br>Only meaningful with --retrieval pull. |
| `--run-max-cost` | `<float>` | Triage, Verify | SHARED_RUN_MAX_COST_USD | `1.0` | Ceiling on what the whole RUN may cost across all its stages, in USD; -1 removes it. Measured against this run's existing metrics records, so a second stage inherits the first's spend.<br>Run-wide; --stage-max-cost bounds this stage alone. |
| `--stage-max-cost` | `<float>` | Triage, Verify | SHARED_STAGE_MAX_COST_USD | `-1.0` | Ceiling on what THIS stage's model calls may cost, in USD; -1 removes the ceiling. Reaching it stops further calls; findings already put to the model stay recorded as asked-but-unanswered, not passed off as judged.<br>Per-stage; --run-max-cost bounds the whole run. |
| `--targets-dir` | `<path>` | Scan, Triage, Verify | SHARED_TARGETS_DIR |  | Directory holding the <name>/target.yml definitions and the source trees they point at. Default: the tool's own targets/. Set it to reach an example-targets checkout outside the tool (the §R1 split).<br>Shared by scan/triage/verify/static-analysis; a target's source_dir is resolved under this directory's parent. |

**Required secrets** — must be set; supply them through the env/secrets file, never on a command line.

| env | needed by | note |
|---|---|---|
| `SHARED_OPENROUTER_API_KEY` | triage, verify (LLM path) | the paid model calls; the deterministic control arms need no key |
| `SCAN_ZAP_API_KEY` | scan | the ZAP daemon's REST key; also settable with `--api-key`, though a key on a command line is visible to every process |

## 3 · Stage 1 · Scan — `dast scan <target>`

> Scan a target: Noir static extraction seeds ZAP's site tree, then a bounded spider and active scan write the raw alerts and an HTTP-exchange sidecar.

**`<target>`** — Which target to scan — a directory under targets/, e.g. `gitea`. It supplies the base URL, the source tree and the path-var defaults.

| flag | value | env | default | description |
|---|---|---|---|---|
| `--zap-addr` | `<url>` | SCAN_ZAP_ADDR | `http://localhost:8080` | Where the ZAP daemon's REST API is reached. The host-published address, not the container name — ZAP is driven from the host, only the scan traffic goes over dast-net. |
| `--api-key` | `<string>` | SCAN_ZAP_API_KEY | `<from SCAN_ZAP_API_KEY>` | The API key the ZAP daemon requires on every REST call. Any non-empty string; it must match the daemon's configured key.<br>Supply it through the env/secrets file — a key on a command line is visible in ps and shell history to every process on the host. |
| `--target` | `<url>` | SCAN_TARGET_URL |  | Override the base URL the scan is pointed at.<br>Falls back to the target's own base URL. |
| `--max-active-scan-minutes` | `<int>` | SCAN_ZAP_MAX_ACTIVE_SCAN_MINUTES | `45` | Cap total active-scan wall time; -1 removes the cap.<br>Bounds the active scanner only — the spider has its own caps (--browser-spider-minutes, --max-rule-minutes bounds each rule). |
| `--max-rule-minutes` | `<int>` | SCAN_ZAP_MAX_RULE_MINUTES | `5` | Cap per-rule active-scan wall time; -1 removes the cap. ZAP applies ONE number to every rule — there is no per-rule timer in its API.<br>Falls back to the target's own `zap_scan.max_rule_minutes`, then the built-in; this flag and the env var outrank the target. |
| `--no-noir, --use-noir` | `—` | SCAN_NOIR_ENABLED | `on` | Skip Noir static extraction and seeding; scan only what the spider crawls unaided.<br>Pairs with --use-noir (the on switch); measures the coverage delta Noir seeding provides (Phase 1 behaviour). |
| `--passive-only` | `—` | SCAN_ZAP_PASSIVE_ONLY | `off` | Run everything up to and including the passive scan — Noir, seeding, the spider, the passive queue — but SKIP the active scan. A legitimate passive baseline: only passive-scanner alerts, no active probing touches the target.<br>A different experiment from a full scan, so it carries its own configuration digest. |
| `--reset-target` | `—` | SCAN_RESET_TARGET | `off` | Reset the target to its clean, freshly-seeded state before scanning (the target stays persistent afterwards), via the target's own env/reset.sh. OFF by default: a persistent target models a permanent CI/CD staging environment, and the state prior authenticated scans accumulate in it (content, settings and the scanner's own footprint) is itself a finding. ON gives each scan a clean starting instance, so scan-volume variance is the scanner's rather than accumulation's.<br>A structural parameter: a reset run carries its own configuration digest. |
| `--noir-source` | `<path>` | SCAN_NOIR_SOURCE_DIR |  | Override the source tree Noir analyses.<br>Falls back to the target's own tree, relative to the repo root. |
| `--noir-image` | `<string>` | SCAN_NOIR_IMAGE | `ghcr.io/owasp-noir/noir:1.2.1@sha256:5332bdb800dc281d4d7067aa14bd15986144f9121b92d7f466c02ba807b00103` | Pinned Noir image. |
| `--zap-mode` | `rest / af` | SCAN_ZAP_MODE | `rest` | How ZAP is driven. `rest` sequences the scan over the REST API — every option is set in one visible place and the run records what it did. `af` hands crawling and scanning to an Automation Framework plan instead (how ZAP is normally driven in CI, more portable), moving those decisions into a YAML this code does not read.<br>`af` takes its plan from --zap-plan. The two modes are NOT comparable runs; the mode is part of the configuration digest. |
| `--zap-plan` | `<path>` | SCAN_ZAP_PLAN |  | The Automation Framework plan for --zap-mode af. A plan named here that does not exist is an error, not a fall-through — naming one is a statement about how the run is driven. The file's SHA-256 is recorded so a result matches the YAML that produced it.<br>Used only with --zap-mode af; falls back to the target's own targets/<name>/zap.yml when it has one. |
| `--keep-zap-session, --keep-session` | `—` | SCAN_ZAP_KEEP_SESSION | `off` | Leave the run's ZAP session file in the daemon instead of removing it. It holds every request and response of the scan, so a run can be reopened in ZAP Desktop — a debugging affordance, not an artifact (gigabytes per run; the message sidecar already carries the exchanges the pipeline reads).<br>Kept sessions accumulate until removed by hand. |
| `--zap-container` | `<string>` | SCAN_ZAP_CONTAINER | `dast-zap` | The daemon's container name. Used only to deliver an automation plan into it with `docker cp` — runPlan takes a path inside the container and the daemon has no bind mount.<br>Relevant only with --zap-mode af. |
| `--spider, --spiders` | `traditional, ajax, client` | SCAN_ZAP_SPIDERS | `traditional,client` | Which crawlers to run, comma-separated and in order: traditional, ajax, client. Order matters — each adds to the tree the previous built, so the cheap HTML pass first means the browser crawlers start from a populated tree.<br>KEEP `traditional` in any list: every recorded coverage number came from it alone, so dropping it moves the baseline. `client` needs a browser (present on the pinned image); its cap is --browser-spider-minutes.<br>Empty falls back to the target's own `spiders:` list, then to `traditional`. |
| `--browser-spider-minutes, --ajax-spider-minutes` | `<int>` | SCAN_ZAP_BROWSER_SPIDER_MINUTES | `5` | Wall-clock cap for EITHER browser-driven crawler (the AJAX and client spiders). Neither reports completion usefully — the AJAX spider has no duration option and the client spider's status is not monotonic (seen climbing to 93 then dropping to 72), so waiting for 100 hangs.<br>The client spider also stops once the tree stops growing; this cap is the backstop. Selected by --spider. |
| `--injectable-targets` | `<int>` | SCAN_ZAP_INJECTABLE_TARGETS | `19` | ZAP injectable-target bitmask, summed: query-string 1, post-data 2, cookie 4, http-headers 8, url-path 16.<br>ZAP's own default omits url-path, which leaves Noir-seeded endpoints uninjectable — this pipeline includes it. |
| `--add-query-param` | `—` | SCAN_ZAP_ADD_QUERY_PARAM | `off` | Let ZAP append a synthetic query parameter to URLs that declare none, reaching inputs no endpoint declares. A finding on it concerns a guessed parameter — report it as a separate scan mode. |
| `--path-var` | `<name>=<value> …` |  | `[]` | Override one route-placeholder substitution, e.g. --path-var username=thesis.<br>Falls back to the target's own path-var defaults. |
| `--disable-rule` | `<rule-id> …` |  | `[]` | An active-scan rule to switch off, by ZAP rule id.<br>With none given, a built-in noisy-rule set is disabled (DEFAULT_DISABLED_RULES); --keep-all-rules runs every rule instead. |
| `--keep-all-rules` | `—` |  | `off` | Run every active rule, including the noisy ones. Reproduces the older behaviour before the noisy rules were disabled; expect rule 10104 to dominate the alerts and heavy ZAP memory use.<br>Overrides --disable-rule's built-in set. |
| `--max-alerts-per-rule` | `<int>` | SCAN_ZAP_MAX_ALERTS_PER_RULE | `-1` | Cap alerts from any single passive rule; -1 removes the cap.<br>ZAP's own baseline uses 10; on this target the cap value did not change the maximum alerts per rule, so whatever it counts is not alerts-per-rule-per-run here. |

## 4 · Stage 2 · Triage — `dast triage <run_id>`

> Triage a finished scan: join ZAP alerts to Noir endpoints, then run the deterministic arm and the LLM arm; writes triage.json.

**`<run_id>`** — Run to triage — its full `<timestamp>-<target>-<config>` id (the directory name in data/), any whole-field prefix of it such as the bare timestamp (completed against data/, erroring if more than one run matches), or `latest`, which means the newest run with both scan artifacts.

| flag | value | env | default | description |
|---|---|---|---|---|
| `--concurrency` | `<int>` | TRIAGE_CONCURRENCY | `10` | Pass-1 calls in flight at once. The calls are independent by design, so this is pure wall-clock: 1 is sequential and the result is identical either way.<br>Lower it if a provider rate-limits; raise it only against a model served by several. |
| `--max-alerts-per-call` | `<int>` | TRIAGE_MAX_ALERTS_PER_CALL | `6` | Starting number of an endpoint's alerts asked about in one pass-1 call (chunked, never dropped). Smaller batches trade more calls for fewer re-asks when a provider returns a short verdict list; the optimum is provider-dependent, so it is measured, not fixed. Env: TRIAGE_MAX_ALERTS_PER_CALL. |
| `--peer-context` | `none / peers / full` | TRIAGE_PEER_CONTEXT | `full` | How much each per-endpoint (pass-1) call is told about its PEER endpoints — where else in THIS scan the same rule fired: `none` (one endpoint per call), `peers` (those peer endpoints), `full` (plus which of them run the same handler). Without it pass 1 cannot know it judged the same rule differently next door; `none` keeps that measurable.<br>Distinct from verify's route `siblings` and from pass 2's cross-endpoint findings. |
| `--http-context` | `<string>` | TRIAGE_HTTP_CONTEXT | `balanced` | How much of each finding's HTTP exchange reaches the prompt — the config/excerpts/<name>.yml to use: none / minimal / balanced / maximum. Storage is generous and excerpting strict, so this is the knob that trades tokens against evidence.<br>The chosen policy file travels verbatim in the artifact. |
| `--code-context` | `none / handler / handler+trace` | TRIAGE_CODE_CONTEXT | `handler+trace` | How much handler SOURCE each pass-1 call gets: `none` (the A/B baseline, not a fallback), `handler` (the resolved handler plus its hop bodies), `handler+trace` (that source plus the call chain followed and where the flagged parameter literally appears).<br>Depth is set by --code-context-hops, the per-endpoint line ceiling by --code-context-lines. |
| `--code-context-hops` | `<int>` | TRIAGE_CODE_CONTEXT_MAX_HOPS | `1` | How many call hops out from the handler to include.<br>The walk saturates after one hop — calls that would go further leave the indexed handler tree. Applies to --code-context handler and handler+trace. |
| `--code-context-lines` | `<int>` | TRIAGE_CODE_CONTEXT_MAX_LINES | `600` | Ceiling on source lines per endpoint. Breadth-first, so what a full budget drops is always further from the handler than what it kept.<br>Bounds the source that --code-context handler/handler+trace emit. |
| `--prompt-cache-triage, --no-prompt-cache-triage` | `—` | TRIAGE_PROMPT_CACHE | `on` | Mark pass 1's system prompt as a cacheable prefix. Worth little here — pass 1's many small calls share only a small header, so little caches.<br>Separately switchable so the writeup's claim that this site is NOT where caching pays stays measurable. --no-prompt-cache-triage is the off form. |
| `--prompt-cache-retrieval, --no-prompt-cache-retrieval` | `—` | TRIAGE_PROMPT_CACHE_RETRIEVAL | `on` | Mark the pull-mode retrieval loop's stable prefix as cacheable. The one site where caching could change a CONCLUSION rather than a bill: pull is a tool-use loop that re-sends the whole conversation each turn, so it spends far more prompt tokens.<br>Applies only with --retrieval pull. --no-prompt-cache-retrieval is the off form. |
| `--no-llm, --use-llm` | `—` | TRIAGE_LLM_ENABLED | `on` | Run the control arm only: the deterministic rescan table, no API key and no spend.<br>The off form of --use-llm. |
| `--screening-prompt` | `<string>` | TRIAGE_PROMPT_VERSION | `3` | Which prompts/screening/screening.v<N>.md to send (pass 1). Pin one to keep a comparison valid when a newer prompt lands — two sheet rows differing only here is a prompt A/B.<br>Falls back to the newest version on disk. |
| `--synthesis-prompt` | `<string>` | TRIAGE_SYNTHESIS_PROMPT_VERSION | `5` | Which prompts/synthesis/synthesis.v<N>.md to send.<br>Falls back to the newest version on disk. |
| `--no-synthesis, --synthesis, --use-synthesis` | `—` | TRIAGE_SYNTHESIS_ENABLED | `on` | Skip the cross-endpoint synthesis pass (pass 2); pass-1 triage still runs. One extra call per run, so this isolates the passes rather than saving cost.<br>The off form of --synthesis. |
| `--prune-noninteractive-php` | `—` | TRIAGE_PRUNE_NONINTERACTIVE_PHP | `off` | Drop php_pure endpoints under cli/ from the LLM arm — a framework-less PHP app's (Cacti's) command-line scripts, which reject HTTP and so only ever carry passive findings on a surface no client reaches. Cuts the corpus the model iterates on; the deterministic record still sees every endpoint.<br>cli/ only (install/ was validated out — the installer is reachable and carries rescan-flagged findings). Off by default and off the WordPress path, where php_pure is dropped wholesale at scan time. |
| `--max-endpoints` | `<int>` | TRIAGE_MAX_ENDPOINTS | `0` | Cap the number of pass-1 model calls; 0 removes the cap. For cost control while iterating on the prompt. |
| `--max-unmatched-findings` | `<int>` | TRIAGE_MAX_UNMATCHED_FINDINGS | `250` | How many findings beyond the old gate pass 1 asks. Every finding of an endpoint with static context is asked; the rest are ranked by ZAP risk, then source before none, and the first N asked, the others recorded as deferred. 0 asks the old gate only; -1 asks every finding. A scope, fixed before any call, so a repeat asks the same. |
| `--screening-max-minutes` | `<int>` | TRIAGE_SCREENING_MAX_MINUTES | `60` | Wall-clock limit on pass 1: no call starts after it, and each unsent call is recorded as a time_limit failure. A safety net set well above a normal run, not a scope; -1 removes it. |
| `--screening-model` | `<string>` | TRIAGE_SCREENING_MODEL | `deepseek/deepseek-v4-flash-0731` | The model for pass 1 (screening: per-endpoint triage). Many small calls, so unit price and latency dominate and reasoning is a liability — it is billed from the completion budget and causes truncation splits.<br>Empty falls back to the pinned pass-1 default. Set per pass — pass 2 has its own --synthesis-model. |
| `--synthesis-model` | `<string>` | TRIAGE_SYNTHESIS_MODEL | `deepseek/deepseek-v3.2` | The model for pass 2 (cross-endpoint synthesis). A handful of calls per run, so unit price barely matters and one long chain of reasoning is everything — the one stage where an expensive model is affordable.<br>Empty falls back to its own pinned default. Use --synthesis-models for an ensemble. |
| `--synthesis-models` | `<string>` | TRIAGE_SYNTHESIS_MODELS |  | Comma-separated models to draw pass-2 samples from, an ENSEMBLE. Each named model draws --synthesis-repeats samples of the same corpus, so the union reports both per-model recurrence and how many MODELS reached each claim — the stronger signal, since repeats of one model share its failure modes.<br>Total pass-2 calls is repeats x models, multiplying the pass's cost. Empty falls back to the single --synthesis-model. |
| `--screening-provider` | `<string>` | TRIAGE_SCREENING_PROVIDER |  | Hard-pin the OpenRouter provider (a slug, or a comma list) for the pass-1 (screening) model — the sibling of --screening-model. A value routes to exactly those providers with fallbacks off (fully reproducible); empty (the default) uses the throughput/require-parameters preference. |
| `--synthesis-provider` | `<string>` | TRIAGE_SYNTHESIS_PROVIDER |  | Provider for the pass-2 (synthesis) model — the sibling of --synthesis-model. Also the default for every --synthesis-models ensemble member, unless --synthesis-providers pins them individually. A value hard-pins with fallbacks off; empty = the throughput/require-parameters preference. |
| `--synthesis-providers` | `<string>` | TRIAGE_SYNTHESIS_PROVIDERS |  | Providers for the --synthesis-models ensemble, matched to it BY POSITION (providers[i] pins models[i]); an empty slot (`a,,c`) leaves that model on the routing preference. A single provider cannot serve models from different vendors, so this is how a heterogeneous ensemble is pinned reproducibly. Its count must equal --synthesis-models' — a mismatch prints an error and SKIPS synthesis (pass 1 is unaffected). Empty (the default) leaves every member on --synthesis-provider. |
| `--synthesis-repeats` | `<int>` | TRIAGE_SYNTHESIS_REPEATS | `5` | How many independent whole-corpus synthesis calls to make, unioned by the evidence each claim cites. Sampling, not chunking — every repeat sees the entire scan, and more repeats surface a reproducible claim more reliably.<br>Each claim carries how many samples produced it, which separates a result from a lead. Multiplied by --synthesis-models. |
| `--synthesis-timeout-seconds` | `<float>` | TRIAGE_SYNTHESIS_TIMEOUT_SECONDS | `5400` | Per-call wall-clock deadline for a synthesis request, in seconds. Set above the slowest completing call ever observed on the frozen model (~59min on a slow provider; p90 ~2min), so it never cuts normal function on any target — it exists only to bound a genuine stall, a provider that accepts the request and never answers.<br>On expiry the pass is SKIPPED (recorded as a 'timeout' failure), pass-1 verdicts stand, and the chain continues to verify. 0 disables the deadline. |
| `--synthesis-max-prompt-tokens` | `<int>` | TRIAGE_SYNTHESIS_MAX_PROMPT_TOKENS | `0` | Pre-emptive synthesis cap: skip the whole-corpus pass WITHOUT attempting it when its estimated prompt exceeds this many tokens. 0 (the default) disables it — synthesis is always attempted.<br>An opt-in size heuristic for a corpus known not to be worth a call; recorded distinctly as an 'oversize' skip. NOT the stall guard (a within-window corpus can still hang) — that is --synthesis-timeout-seconds. |

## 5 · Stage 3 · Verify — `dast verify <run_id>`

> Verify triaged findings with independent tools — one bounded loop per finding, the third and last reading (after the deterministic table and LLM triage): a tool actually trying the attack, recorded confirmed / refuted / inconclusive / not-attempted.

**`<run_id>`** — Run to verify — its full `<timestamp>-<target>-<config>` id (the directory name in data/), any whole-field prefix of it such as the bare timestamp (completed against data/, erroring if more than one run matches), or `latest`, which means the newest run with a triage.

| flag | value | env | default | description |
|---|---|---|---|---|
| `--invocation` | `llm / deterministic` | VERIFY_INVOCATION | `llm` | HOW the tool is called, and when to stop asking. `llm` runs the round loop: every verdict-moving fix in this project's history was about invocation, never tool choice (which is always the deterministic lookup). `deterministic` is the fixed single-shot probe — the FULLY-DETERMINISTIC configuration, no key, no spend, the control every LLM configuration is measured against. |
| `--max-rounds` | `<int>` | VERIFY_MAX_ROUNDS | `3` | Rounds one loop may run before it must conclude (propose, react, refine). With the per-run cost ceiling this bounds the loop's spend — a runaway loop is a mistake to make impossible.<br>Ignored under --invocation deterministic, which is single-shot by nature. |
| `--max-dispatch-all-rules` | `<int>` | VERIFY_MAX_DISPATCH_ALL_RULES | `30` | Dispatch cap for every ZAP rule that --max-dispatch-rule does not name; -1 disables it. Without a ceiling here one noisy passive rule owns the whole verification budget — rule 10031 alone supplies most flags on Gitea. This layer decides COVERAGE: it drops findings, it never shortens the ones it keeps.<br>Overridden per rule by --max-dispatch-rule; bounded by --max-dispatches-total. |
| `--max-dispatch-rule` | `<id>=<n> …` | VERIFY_MAX_DISPATCH_RULE | `[]` | Dispatch cap for ONE ZAP rule, as ID=N (e.g. 40018=40); -1 disables the cap for that rule, 0 never dispatches it. Several assignments may be comma-separated in one argument or given as repeated flags. On a noisy target most budget refusals are the per-rule cap, and a single blanket number could not let one rule run further without moving every other with it.<br>Overrides --max-dispatch-all-rules for the named rule; never outlives --max-dispatches-total, which ends the run whatever a rule was still allowed. |
| `--max-dispatches-total` | `<int>` | VERIFY_MAX_DISPATCHES_TOTAL | `40` | Cap tool invocations for the WHOLE RUN; -1 disables it. Cross-endpoint, not per endpoint: one number for the stage, which is what `_total` says.<br>The outer bound over --max-dispatch-all-rules and --max-dispatch-rule; reaching it ends the run. |
| `--max-minutes` | `<int>` | VERIFY_MAX_MINUTES | `20` | Wall-clock cap for the dispatch stage; -1 disables it. Disabled together with the count caps it is an EXHAUSTIVE run — every selected finding dispatched, nothing left not-attempted for a budget reason.<br>An exhaustive run is then bounded only by --tool-timeout per invocation, so size it before starting one. |
| `--tool-timeout` | `<int>` | VERIFY_TOOL_TIMEOUT_SECONDS | `150` | Hard timeout for one tool invocation; a kill is recorded inconclusive, never refuted.<br>The per-invocation bound that backstops an exhaustive --max-minutes -1 run. |
| `--prompt-cache-verify, --no-prompt-cache-verify` | `—` | VERIFY_PROMPT_CACHE | `on` | Mark the verification loop's stable prefix as cacheable. Each round re-sends the system prompt, the finding, the handler source and every prior round's output, so most of its prompt tokens are a cacheable stable prefix.<br>--prompt-cache is the master switch for all multi-turn caching; --no-prompt-cache-verify is this site's off form. |
| `--oracle-seed-dispatch` | `—` | VERIFY_ORACLE_SEED_DISPATCH | `off` | Oracle-seeded verify dispatch (needs --oracle). For every ground-truth marker whose documented sink raised no ZAP finding, synthesise a dispatch FROM THE MARKER — the sink URL, the tool the rescan table routes the marker's rule to, and the marker's auth — so a CVE whose in-band ZAP reach is budget-bound (Cacti's CVE-2022-46169 at the authenticated ceiling) is still confirmed out of band. A LABELED ADDITIONAL configuration: the verdict still resolves through resolve_verdict and the record is marked oracle-seeded, never counted with blind detections.<br>Off by default and ignored without --oracle, so it can never touch a blind run and the baseline's artifacts are byte-identical. |
| `--max-siblings` | `<int>` | VERIFY_MAX_SIBLINGS | `0` | Turn ON the propagation dispatch and cap it at N unflagged sibling routes per claim; 0 is off, 3 the sensible value when on. These are routes a cross-endpoint claim PREDICTS share a weakness and the scan never flagged; a confirmation on one is a finding no part of the deterministic pipeline could reach.<br>Off by default: it changes what a run contains (extra dispatches, a new finding class, a target reached over dast-net), so a run with it is not comparable to one without, and it is so far unvalidated — two live runs, zero confirmations. |
| `--interactsh-server` | `<url>` | VERIFY_INTERACTSH_SERVER | `http://target-interactsh:8080` | Self-hosted interactsh sink for out-of-band confirmation. Never the public oast.pro pool — it would send this target's out-of-band interactions to someone else's server.<br>Used only when --oob is on. |
| `--nuclei-templates-volume` | `<string>` | VERIFY_NUCLEI_TEMPLATES_VOLUME | `nuclei-home` | Named Docker volume holding the pinned nuclei templates; the image ships none.<br>Populate it once with -update-templates, then it runs offline. |
| `--oob, --no-oob` | `—` | VERIFY_OOB | `off` | Arm out-of-band (OAST) nuclei templates against the self-hosted interactsh sink. On Gitea it changed no verdict and roughly tripled the stage's wall time, its only OOB item needing git operations DAST cannot reach; turn it on for a target with reachable SSRF or blind-injection surface.<br>Needs --interactsh-server; --no-oob is the off form. |
| `--model` | `<string>` | VERIFY_MODEL | `minimax/minimax-m2.5` | The ONE model the whole loop uses — every round's invocation proposal and its final category. Always a dated/immutable snapshot, never a floating alias: a re-run whose weights moved is not a reproduction.<br>Has its own pinned default and does NOT inherit the triage model: a stage's model is set per stage, never bled in from another.<br>Unused under --invocation deterministic, which calls no model. |
| `--provider` | `<string>` | VERIFY_PROVIDER |  | Hard-pin the OpenRouter provider (a slug, or a comma list) for the verify model — the sibling of --model (VERIFY_MODEL/VERIFY_PROVIDER). A pinned model routes to exactly those providers with fallbacks off (fully reproducible); empty (the default) uses the throughput/require-parameters preference. |
| `--verify-prompt` | `<string>` | VERIFY_PROMPT_VERSION | `2` | Which prompts/verify/verify.v<N>.md the loop sends. Pinned the same way as the triage prompts, so a harness row can A/B the wording.<br>Falls back to the newest version on disk. |

## 7 · Static-analysis — `dast static-analysis <target-or-run>`
